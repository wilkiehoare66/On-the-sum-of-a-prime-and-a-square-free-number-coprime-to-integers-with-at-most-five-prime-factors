# On the sum of a prime and a square-free number coprime to integers with at most five prime factors

[![DOI](https://zenodo.org/badge/1322756247.svg)](https://doi.org/10.5281/zenodo.21813035)

Code for the verifications required in the paper *"On the sum of a prime and a
square-free number coprime to integers with at most five prime factors"* by
W. Hoare, E. S. Lee and A. Pearce-Crump.

## What has to be true for the theorem to hold

The proof has two computational halves, and both are here.

* **Analytic** (Python). Explicit lower bounds for `R_k(n)` (Proposition 4.1)
  and upper bounds for `B_q(n)` (Proposition 4.3), assembled into the five-case
  division of Lemma 5.4 that covers *every* odd square-free `k` with
  `omega(k) = 5`. Valid for `n >= 8e9`.
* **Finite** (C++, plus one Python script). Exhaustive verification over
  `108 <= n <= 2e12`. The two halves meet far inside the verified range.

## Requirements

* Python 3.8+ (standard library only; `sympy` is *not* required)
* A C++17 compiler with OpenMP (`g++ -fopenmp`)
* The four data tables must be present in the repository root:
  `bennett_c_theta.tsv`, `bennett_x0.tsv`, `rr_theta_table1.tsv`,
  `rr_theta_table2.tsv`. The analytic scripts abort rather than silently fall
  back to the weaker envelope constants, which would not reproduce the paper.

## Reproducing the analytic constants

```
python3 ComputeRkBound.py --k 105          # Corollary 4.2
python3 ComputeBqBound.py --bq 13          # Proposition 4.3
python3 CoverageTree.py --omega 5          # regenerates Table 3 (Lemma 5.4)
python3 CertifyCases.py                    # writes case_certificates.json
python3 VerifyCertificate.py               # re-checks it; exit status is the verdict
python3 verify_R_classes.py
```

`CoverageTree.py --omega 6` reproduces Table 4: the ten moduli that defeat the
method at six prime factors.

### The toggles

Proposition 4.1 is sharpened in two independent ways: the Brun-Titchmarsh loss
factor is weighted pointwise across the sieve range rather than replaced by its
endpoint value, and the coprimality condition is retained inside that range
rather than discarded. Proposition 4.3 carries the first of these. Neither
touches the main term, the short-range error, or any imported estimate.

`ComputeRkBound.py` and `ComputeBqBound.py` each carry a flag (`SHARPEN`,
`SHARPEN_B`) restoring the unsharpened form of its proposition, so that a
reader can switch the sharpenings off and see exactly what they are worth:

| quantity | unsharpened | sharpened |
|---|---|---|
| `R_3(n)/n`   | 0.16812 | 0.19452 |
| `R_15(n)/n`  | 0.09527 | 0.15123 |
| `R_51(n)/n`  | 0.05555 | 0.16205 |
| `E_B(13)`    | 0.02036 | 0.01566 |

With the flags off, `k = 105` has no positive direct bound below
`n ~ 1.77e11`; with them on it is positive at `8e9` with margin `+0.111`.

### Directed rounding

Every printed bound is rounded in the safe direction — main terms and margins
down, error terms up. Artin's constant is replaced by the strict lower bound
0.3739558; the products of local factors are formed as exact rationals and
rounded only at the last step; a safety envelope is subtracted from every
margin, far above the measured floating-point error. Because the admissible set
of imported bounds changes at `x = 1e10`, each margin is certified separately
on `[8e9, 1e10]` and on `(1e10, inf)`; every error term decreases in `n` on each
interval, so the left endpoint is a rigorous minimum for the margin.

## Reproducing the finite verification

The range splits at `1e4`, and this is a mathematical split, not an
optimisation. The C++ device certifies `n` by exhibiting six *pairwise coprime*
witnesses, which is sufficient but not necessary. At `n = 167` no such six exist
even though `n = 167` is good for every `omega(k) <= 5` — the least covering set
of the witness supports has six elements while the largest pairwise coprime
subfamily has five. So:

```
python3 Threshold.py --rmax 5 --certify 108 10000     # exact criterion, seconds
```

covers `108 <= n <= 1e4`, and the C++ covers the rest. `Threshold.py` also
reproduces the published thresholds 36 and 60 (with the moduli 33 and
`759 = 3*11*23`), which is what validates it:

```
python3 Threshold.py --rmin 2 --rmax 6 --nmax 3000
```

### The C++ run

Build without `-DUSE_BPSW`: the results of record use the unconditional
twelve-base Miller–Rabin test of Sorenson–Webster. The BPSW variant is faster
but exhaustive only conjecturally.

```
cd verification
g++ -O3 -fopenmp -std=c++17 -o verify_odd  verify_odd.cpp
g++ -O3 -fopenmp -std=c++17 -o verify_even verify_even.cpp

./verify_odd  --selftest && ./verify_odd  --test
./verify_even --selftest && ./verify_even --test

export OMP_NUM_THREADS=$(nproc)
bash run_manifest.sh                 # provenance, BEFORE the run
./verify_odd                         # resumable with --resume
./verify_even
bash run_manifest.sh                 # provenance, AFTER the run
python3 verify_results.py --sample 200
```

Both are resumable (`--resume`) and checkpoint once per batch, so a killed run
loses at most the current batch.

The witness and split counts appear in exactly one place each —
`NUM_WITNESSES` in `verify_odd.cpp`, `NUM_SPLITS` in `verify_even.cpp` — and
`verify_results.py` carries copies that must be kept in step with them.

`verify_large_prime.cpp` is an independent cross-check inherited from the
first author's thesis. It is not cited by the paper and running it is optional.
